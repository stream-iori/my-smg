# 资源控制：先确定维度，再选择方案

[分类目录](index.md) · [总入口](../index.md) · [流式内存与背压](streaming-memory.md)

**先确定保护什么资源、怎样计量和超限后怎么办，再选择信号量、令牌桶或其他机制。多个控制可以组合。**

## 设计维度

| 维度         | 要回答的问题             | 可选值或例子                                         |
| ------------ | ------------------------ | ---------------------------------------------------- |
| 控制对象     | 限制什么？               | 请求、连接、任务、队列、缓冲、上游节点               |
| 计量单位     | 用什么衡量？             | 请求数、请求/秒、字节数、token 数、并发数、等待时间  |
| 控制范围     | 对谁生效？               | 全局、单实例、单节点、单模型、单用户、单请求         |
| 时间范围     | 关注瞬间还是一段时间？   | 当前并发、每秒速率、滑动窗口、累计用量、最长持续时间 |
| 控制位置     | 在哪里拦截或施压？       | 接入前、排队前、调用上游前、流式传输中               |
| 超限行为     | 达到上限后怎么办？       | 等待、排队、拒绝、丢弃、降速、取消                   |
| 隔离与公平   | 容量如何分配？           | 共享池、用户配额、模型配额、优先级、公平排队         |
| 阈值来源     | 上限怎么确定？           | 固定配置、按资源预算计算、根据负载动态调整           |
| 资源生命周期 | 从何时开始计，何时释放？ | 请求进入到响应头、到正文结束、到后台任务真正退出     |
| 观测与验证   | 怎样知道限制有效？       | 活跃数、队列长度、等待耗时、拒绝数、内存和延迟       |

```text
控制对象 + 计量单位 + 控制范围 + 时间范围
                    ↓
           在哪里控制、超限后怎么办
                    ↓
           如何分配、何时释放、怎样验证
                    ↓
                 选择机制
```

## 控制目标与机制

| 想控制什么             | 合适方案                 | 与信号量的关系                       |
| ---------------------- | ------------------------ | ------------------------------------ |
| 同时执行多少个请求     | 信号量                   | 直接适用：每个请求占一个名额         |
| 每秒接收多少请求       | 令牌桶                   | 控制速率，通常与信号量配合           |
| 排队多少条数据         | 有界 `mpsc`              | 控制队列长度；不自动限制字节数       |
| 缓冲占多少内存         | 字节预算、单块大小限制   | 补充信号量：请求数有界不代表内存有界 |
| 不同用户或模型互不抢占 | 分组信号量、配额或调度器 | 在全局限制之外增加隔离               |
| 根据负载动态调整容量   | 自适应并发控制           | 需要延迟、错误率等指标和验证         |

单个限制只保护它计量的对象：例如限制活跃流数不会自动限制每条流的缓冲字节，也不会限制所有 TCP 连接。

## 项目例子：流式请求并发

| 维度            | 当前选择                                      |
| --------------- | --------------------------------------------- |
| 控制对象 / 单位 | 活跃请求数，每个请求占一个执行名额            |
| 范围            | 单个网关实例，普通请求和流式请求共享          |
| 时间范围        | 当前并发                                      |
| 控制位置        | handler 中，选择上游前；请求提取已发生        |
| 超限行为        | 最多 2 个请求等待 300ms；队满或等待超时则拒绝 |
| 生命周期        | 流式正文持有执行凭证，直到正文结束或清理      |
| 机制            | 信号量限制执行和等待，另用令牌桶限制请求速率  |

当前执行并发上限为 2，是教学配置，不代表生产容量。代码见 [main.rs](../../../src/main.rs)、[gateway_state.rs](../../../src/gateway/gateway_state.rs) 和 [chat_stream.rs](../../../src/gateway/chat_stream.rs)。

## 自查

| 问题                                             | 应能说明的点                                       |
| ------------------------------------------------ | -------------------------------------------------- |
| 限制 100 个请求，内存一定有上限吗？              | 还需要考虑每个请求的大小、其他连接和缓冲           |
| 限制每秒 100 个请求，并发一定不超过 100 吗？     | 不一定；请求持续时间会影响并发数量                 |
| 流式响应返回响应头时释放名额，可以限制活跃流吗？ | 不可以；正文可能仍在传输，应按目标确定凭证生命周期 |
